# Правила работы над PPRBot

## Архитектура

PPRBot состоит из следующих основных компонентов:

- `backend/` — Python-приложение на FastAPI, SQLAlchemy, aiogram и APScheduler.
- `backend/app/api/` — HTTP API, авторизация Telegram Mini App и управление ролями.
- `backend/app/bot/` — Telegram bot polling, команды, inline-кнопки и обработка статусов.
- `backend/app/db/` — модели SQLAlchemy, сессии и подключение к базе данных.
- `backend/app/excel/` — чтение Excel, preview/apply безопасного импорта и сопоставление строк.
- `backend/app/services/` — бизнес-логика ППР, dashboard, доставки Telegram, Outlook Graph и полной замены расписания.
- `backend/app/scheduler/` — периодические backend-задачи, включая опциональный автоимпорт Excel.
- `frontend/` — React + TypeScript + Vite Telegram Mini App.
- `alembic/` — версионируемые миграции схемы базы данных.
- `scripts/` и `deploy/` — запуск, остановка, backup/restore и deployment для Windows/Linux.
- `data/` — исходное Excel-расписание и локальные данные; production-данные не следует считать файлами приложения.

Основной поток данных: Excel → импорт и валидация → PostgreSQL (`ppr_events`, `ppr_notifications`) → FastAPI API и Telegram bot → Mini App и Telegram-сообщения.

PostgreSQL является основной базой данных проекта. Локальные SQLite-файлы и прочие артефакты в `data/` не заменяют PostgreSQL.

FastAPI и Telegram bot запускаются отдельными процессами. FastAPI обслуживает API и собственный scheduler, а `python -m app.bot.runner` отвечает за Telegram polling и автоотправку уведомлений. Нельзя считать запуск только одного из этих процессов полноценным запуском системы.

## Правила изменения кода

1. Перед изменениями необходимо изучить существующую реализацию, связанные компоненты и релевантные тесты.
2. Нельзя менять существующее поведение без явной необходимости и подтверждённого требования. Совместимость с текущими режимами `bot_only` и `full` нужно сохранять.
3. Все изменения структуры или данных базы данных выполняются только через Alembic-миграции. Не следует исправлять production-схему через `create_all`, ручной SQL или прямое редактирование базы.
4. Для новой функциональности необходимо добавлять или обновлять тесты. Тесты должны покрывать не только успешный сценарий, но и важные ошибки, права доступа и защитные ограничения.
5. После изменений необходимо запускать релевантные тесты, а перед завершением задачи — полный backend test suite.
6. Не выполнять массовую отправку Telegram-сообщений, реальную синхронизацию Outlook или команды, изменяющие production-данные, без отдельного явного разрешения.
7. Не выводить и не коммитить токены, пароли, содержимое `.env`, секреты Outlook, Telegram initData и любые другие секретные значения. Использовать `.env.example` для документации конфигурации.
8. Перед завершением задачи необходимо проверить `git diff` и `git status`, убедившись, что изменения ограничены согласованной областью.

## Безопасность и эксплуатация

- Во время пилота сохранять безопасные флаги автоотправки, если отдельным требованием не разрешено иное: `NOTIFICATIONS_AUTO_SEND_ENABLED=false`, `PILOT_AUTO_SEND_ALLOWED=false`, `AUTO_SEND_ALLOW_MASS=false`.
- Перед полной заменой расписания из Excel использовать preview; применение требует предусмотренного проектом подтверждения и backup.
- Учитывать, что Outlook-синхронизация использует Microsoft Graph и изменяет ссылку события в базе данных.
- Не удалять, не восстанавливать и не перезаписывать production-данные без явного разрешения и проверки точной области операции.

## Требования к итоговому отчёту

В итоговом отчёте по каждой задаче нужно указывать:

- изменённые файлы;
- выполненные тесты и команды проверки;
- результат каждого существенного тестового запуска;
- оставшиеся риски, ограничения или непроверенные сценарии.
